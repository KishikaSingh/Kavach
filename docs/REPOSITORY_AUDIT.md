## 2. Architecture — Confirmed Findings

### 2.1 Which firmware is authoritative?

**`firmware/KavachHelmet/`** (KavachHelmet.ino) is the team's production reference firmware.

- Authenticates with Firebase using a **custom token** provisioned by `backend/functions/scripts/provision-device.js`.
- Stores the Firebase refresh token in ESP32 NVS (Preferences library).
- Sends telemetry every 10 s via HTTPS PATCH to `/devices/{deviceId}.json`.
- Sends SMS directly via SIM900A over GSM (hardware fallback — completely independent of cloud).

`firmware/smart_helmet/` is an **earlier prototype**. It authenticates with email/password (rejected by current DB rules) and is kept for its modular unit-testable C++ logic only. **Do not flash it.**

### 2.2 Database: RTDB or Firestore?

**Firebase Realtime Database (RTDB)** exclusively.

Confirmed paths:
- `/devices/{deviceId}` — helmet telemetry
- `/alerts/{deviceId}/{alertId}` — accident events
- `/deviceOwners/{deviceId}/{uid}` — admin-only allowlist
- `/users/{uid}/contacts`, `/users/{uid}/notifications`, `/users/{uid}/settings`, `/users/{uid}/pushTokens`
- `/pushDispatches/{deviceId}/{alertId}` — idempotency lock
- `/pushReceipts/{uid}/{ticketId}` — Expo delivery tracking
- `/smsDispatches/{deviceId}/{alertId}` — AWS SNS outcome records

### 2.3 Confirmed accident event

**Trigger:** Firebase Cloud Function `onAccidentAlertCreated` using `onValueCreated` on `/alerts/{deviceId}/{alertId}`.

**Stable event ID:** `{deviceId}/{alertId}` — the alertId is generated by the ESP32 firmware using a UUID-like key, and the combination is used as the idempotency key stored at `pushDispatches/{deviceId}/{alertId}`.

**Idempotency:** Atomic Firebase RTDB transaction on `pushDispatches/{deviceId}/{alertId}` — if `status === 'sent'` already, the function returns null. If `status === 'sending'` and less than 5 minutes old, it throws to trigger a retry. This correctly prevents duplicate dispatch.

### 2.4 Emergency contact path

**App contacts:** `/users/{uid}/contacts/{contactId}` — objects with `{ name, phone, isPrimary }`.

**Firmware SMS recipient:** `SMS_RECIPIENT_E164` in `firmware/KavachHelmet/config.h` — **not synced** from app contacts. The two notification channels (firmware GSM and cloud AWS SNS) use separate recipient lists by design.

**Cloud dispatch reads:** `users/{uid}/contacts` from Firebase Admin SDK inside `publishAccidentAlert()` in `backend/functions/index.js`.

### 2.5 SMS dispatch path

```
Firebase RTDB (/alerts/{deviceId}/{alertId} created)
    → Cloud Function: onAccidentAlertCreated
        → claimDispatch() [atomic RTDB transaction — idempotency lock]
        → publishAccidentAlert()
            → reads /deviceOwners/{deviceId}
            → for each owner uid:
                → reads /users/{uid}/settings, pushTokens, profile, contacts
                → dispatchEmergencySms(contacts, alert, userName)  [awsSns.js]
                    → normalizePhoneNumber()
                    → SNSClient.send(PublishCommand{ PhoneNumber, Message })
                → writes smsStatus back to /alerts/{deviceId}/{alertId}
                → writes smsDispatches/{deviceId}/{alertId}
                → sendExpoPushMessages()  [expoPush.js]
    → writes pushDispatches status = 'sent'
```

## 3. Critical Bugs Identified

### BUG-001: IAM Policy Resource Mismatch (BLOCKING)

**Severity:** Critical — SMS dispatch will fail with `AccessDenied` if Terraform is applied as-is.

**Location:** `terraform/main.tf`, lines 47-64.

**Problem:** The policy grants `sns:Publish` only to `aws_sns_topic.emergency_alerts.arn` (a specific topic ARN). However, `backend/functions/awsSns.js` publishes **directly to phone numbers** using `SNSClient.send(PublishCommand{ PhoneNumber: "+91..." })` — not to any topic.

For direct-to-phone SMS, AWS SNS requires `sns:Publish` with `Resource: "*"`. SNS does not support resource-level permissions for direct SMS publish to phone numbers.

**Fix:** Change the IAM policy resource to `"*"` with an explicit `sid` documenting the reason, and add a condition restricting the sender ID format.

### BUG-002: IAM Access Key Managed in Terraform State (SECURITY)

**Severity:** High — The existing `terraform/main.tf` creates an `aws_iam_access_key` resource. This stores the secret access key in the Terraform state file in plaintext. Anyone with state file access can read the secret.

**Fix:** Remove `aws_iam_access_key` from Terraform. Manage access key creation and rotation outside Terraform using AWS Console or CLI. Store credentials in a secrets manager, not state.

### BUG-003: Secret Access Key Exposed in Terraform Output

**Severity:** High — `outputs.tf` outputs `aws_secret_access_key` as a sensitive value. Even with `sensitive = true`, the value is stored plaintext in `terraform.tfstate` and visible via `terraform output -raw aws_secret_access_key`.

**Fix:** Remove this output. After removing the `aws_iam_access_key` resource, this output has no source.

### BUG-004: SNS Topic Used for Email Only, Not Required for SMS Dispatch

**Severity:** Medium — The existing Terraform creates `aws_sns_topic` for email subscriptions, but the actual cloud SMS dispatch in `awsSns.js` does not use any SNS topic. This creates an unused resource that incurs costs.

**Fix:** Retain the topic only if email alerting is desired. Document clearly that it is separate from the Firebase Cloud Function SMS dispatch path.

### BUG-005: No Transactional SMS Type Configuration

**Severity:** Medium — `awsSns.js` correctly sets `AWS.SNS.SMS.SMSType: Transactional` per-message. However, the account-level SMS default type is not set via Terraform, meaning it defaults to `Promotional` unless configured.

**Fix:** Add `aws_sns_sms_preferences` resource to set account-level defaults.

### BUG-006: No CloudWatch Logging or Observability

**Severity:** Low-Medium — There is no CloudWatch log group, metric or alarm for SMS dispatch failures. Operational visibility into dispatch success/failure rates requires manual console inspection.

**Fix:** Add observability module with CloudWatch log groups for Cloud Functions and operational alarms.

### BUG-007: Terraform Not Modularized / No Environment Separation

**Severity:** Low (operational risk) — All configuration is in a single flat directory with no environment-specific variable files, making dev/staging/prod separation impossible.

**Fix:** Refactor into modular structure with environment tfvars examples.

## 4. Architecture Decision: Firebase CF → SNS Direct vs API Gateway + Lambda

**Decision: Keep Firebase Cloud Function → SNS direct publish. Do not add API Gateway + Lambda.**

**Rationale:**
1. The trigger is **internal** (Firebase RTDB event → trusted Cloud Function environment). There is no external HTTP caller that needs an authenticated endpoint.
2. The existing Cloud Function already has strong idempotency via atomic RTDB transactions.
3. Adding API Gateway + Lambda adds ~3 network hops, additional attack surface, new IAM roles, and deployment complexity without a proportional security or reliability benefit.
4. The direct architecture is already tested (12/12 backend tests pass, 56/56 frontend tests pass).
5. A Lambda function would need the same AWS credentials as the Cloud Function, solving the same auth problem in a more complex way.

**What this audit recommends:**
- Fix the IAM policy (BUG-001 — critical blocker).
- Remove access key from Terraform state (BUG-002).
- Modularize Terraform for maintainability.
- Add SNS SMS preferences, CloudWatch log groups, environment separation.
- Document credential provisioning process clearly.
